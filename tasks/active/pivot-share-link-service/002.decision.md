# Full rebrand, API-first, behind a KV backup/restore gate

Resolves the open question from [[001.draft]] (thin rebrand vs full rename).

## Decisions

1. **Full rebrand** — rename the `mdcv` domain (collection, routes, DTO, service)
   to the generic share-page-via-link noun. Not a thin UI-only rebrand.
2. **API-first scope** — this task covers the API only. The UI rebrand is
   accepted as a given ("will be rebranding absolutely") and is deferred /
   out-of-scope here; it follows once the API surface is stable.
3. **Backup/restore gate** — a full rename touches collection keys, so we do not
   mutate live KV without a backup + a tested forward migration. Two subtasks
   own this and must land before the rename:
   - [[kv-dump-script]] — dump current KV (remote, via `ACCESS_TOKEN` +
     `deno kv` / `Deno.openKv` connect URL).
   - [[kv-restore-migrate]] — restore a dump into the new schema, mapping
     old (CV-shaped) records → new (generic page) shape.
4. **Preserve the render-decision logic** — the artifact-vs-fallback logic
   currently imperative in `render_cv` (api/spa_subserver/spa_subserver.tsx):
   `kind:"pdf"` → serve the uploaded artifact; else render md→html in our
   `SimpleLayout` (our site); missing blob → degrade to markdown. During the
   migration this must be retained and is to be expressed as an **xstate
   machine**: resolve → `serve_artifact` (target shareable artifact) |
   `fallback_to_site` (our rendered page), with the degrade edge.

## Consequence

This task is **blocked** on [[kv-dump-script]] and [[kv-restore-migrate]].
No rename/code on the `mdcv` domain until a dump exists and a restore-into-new
-schema path is proven. Switching focus to [[kv-dump-script]] first (restore
depends on a dump existing).
