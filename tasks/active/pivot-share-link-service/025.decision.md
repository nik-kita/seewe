# Slice 7 data move: offline transform to a saved fixture, restore after deploy

The old->new data migration is split into a PRODUCE step (now) and an APPLY step
(deferred), instead of transforming on restore in one shot. User-confirmed.

- **Produce (now):** dump remote KV verbatim, then transform OFFLINE into a
  new-schema **fixture file** kept on disk. No live KV is written.
- **Apply (deferred):** only after the rebranding is finished + deployed do we
  restore the fixture into remote KV. Rationale: don't touch live data before the
  new schema is fully shipped; the fixture is a reviewable, re-runnable artifact.

Mechanism decided: **replay through kvdex**, not raw key surgery. Restore the
dump into a throwaway local kv, read old docs via the real schema, re-write as
`page` docs through the app's own write paths -> correct indices + v8-chunked pdf
segments for free. This required extracting `db.ts` into a `make_db(kv)` factory
so the schema isn't duplicated.

Migration fidelity rule: routing keys derive ONLY from the old index markers
actually present (`as_regulary_by_name_username`, `as_default_by_*`), never
re-derived from `name`. Several legacy records share a `name` without the old
compound index (dupes); re-deriving would collide on the new `by_username_and_name`
primary key. Faithful = those stay link-unreachable (orphan), exactly as before.

Supersedes the earlier "transform on restore" framing of the `transform_entry`
seam in [[kv-restore-migrate]] — that seam stays identity; the transform lives in
the standalone produce step. Executed in [[026.log]].
