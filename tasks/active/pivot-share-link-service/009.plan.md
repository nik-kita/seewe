# Lean into the link: render cache + reserved-username guard

Two concept-level features for [[seewe-core-link-concept]], following "any
sacrifice for the link".

## 1. Denormalization depth — eliminate render from the hot path

Key insight: on the link path the expensive step is NOT the index get (1 fast,
strongly-consistent kvdex lookup) — it is the RENDER. PDF already read-through
caches by `_id/pdf_version/variant`; markdown re-runs `md_to_html` + JSX on
EVERY hit. So denormalization should target render elimination, keeping the
single consistent index get.

Ladder:
- L0 now: 1 get + render-per-hit (md).
- L1: Cache-Control headers -> browser/edge cache. Cheap outer layer; TTL-coarse.
- L2: read-through Web Cache for the md render too, keyed by
  `_id/render_version/variant` (mirror the pdf cache). Render runs only on first
  hit after an edit.
- L3: URL-keyed full-Response cache (zero KV on warm hits), invalidated by
  explicit purge of a page's URLs on every write.

Decision lean: **L2 + L1**, NOT L3. Why not L3: Deno Deploy's Web Cache is
regional/best-effort, so purge-based invalidation can't reliably evict other
regions -> stale risk. Version-IN-KEY (L2) is self-correcting: a read computes
the current version from the fresh page record and forms a new key; old-version
entries are simply never requested again (same self-orphaning as `pdf_version`).
The kept index get is cheap and consistent; the render is what we remove.

Schema: unify into one `render_version: number`, bumped on any content/representation
change (md, css, pdf replace, kind flip) — replaces/extends `pdf_version`. The
xstate render machine wraps both arms: resolve -> (serve_artifact | render_md)
-> versioned read-through cache. Optional: warm the cache on write (helps only
the authoring region; read-through covers the rest).

## 2. Reserved-username guard (generated)

No guard today; usernames share the root namespace with app routes -> a nik can
shadow `/dashboard` etc. Build a generated reserved set, checked in `add_nik` /
`update_nik` (users_service), normalized lowercase, EXACT match.

Sources (union, dedup):
- OWN app slugs — authoritative, AUTO-GENERATED from vue-router routes so it
  stays in sync. Today: about, dashboard, dev, home, md-cv, pdf-cv, settings
  (+ post-rename: page, login, signup, logout, ...).
- Root/infra prefixes: v1, openapi, id, content, auth, users, page(mdcv), json,
  assets, static, public, favicon, robots, sitemap, .well-known, api, www, cdn, app.
- Brand/role/impersonation + RFC 2142 role mailboxes: admin, administrator, root,
  support, help, contact, official, staff, team, system, security, abuse, billing,
  status, postmaster, webmaster, hostmaster, noc, me, null, undefined, anonymous.
- Profanity/toxic.

External lists I can name:
- The Big Username Blacklist (marteinn, MIT, ~1500) — already merges routes/brand
  /infra/offensive; good single base.
- LDNOOBW "List of Dirty Naughty Obscene And Otherwise Bad Words" (multilingual)
  for profanity breadth. (npm `bad-words` / `leo-profanity` are runtime alts.)

Build: a dev script (kv_dump/schema_snapshot family) emits a committed
`reserved-usernames.ts` (a `Set<string>`) from bundled lists + our route slugs;
regenerate when routes change. Enforce case-insensitively after normalizing the
candidate (lowercase; min len already 3 via UserDto).

Open risk to confirm: profanity matching = EXACT (avoids the Scunthorpe false-
positive problem) vs fuzzy/substring (catches leet/embeds but blocks legit
names). Recommend exact for v1.
