# The core concept: link = domain/username(/name), resolved first; site is fallback

Found the pivot moments that declare the project's defining feature. The DB
design must serve THIS, not the other way round.

## Where the concept lives in code

1. `api/mod.ts:19-22` — route precedence:
   - `/v1/*`, `/openapi/*` carved out first (explicit app namespaces).
   - `spa_subserver` mounted at `/` — it OWNS the root namespace.
   - `app.notFound(serve_static)` — the site/SPA is the FALLBACK.

2. `api/spa_subserver/spa_subserver.tsx` route order = the concept:
   - `/id/:user_id` (104) — anon / pre-username default page.
   - `/:username/:cv_name` (143) — `domain/username/name`.
   - `/:username` (167) — `domain/username`.
   - `.get("*", serve_static)` (233) — fall back into the site.
   The username space IS the root. You reach the site only when the path is not
   a username/page.

3. The link resolves in ONE direct primary-index get:
   - `/:username/:name` -> `findByPrimaryIndex("as_regulary_by_name_username",
     [username, name])` (146).
   - `/:username` -> `findByPrimaryIndex("as_default_by_username", username)`
     (171).
   Those two index FIELDS exist precisely to make the sacred link a single
   direct lookup.

## Retraction

My proposed `user_id`-centric routing (resolve nik -> user_id -> page) is WRONG:
it turns `/:username` and `/:username/:name` into TWO gets to save a rare
rename cost. That sacrifices the defining path for write-side tidiness —
backwards. Retracted.

## Subtlety it would have broken: dual addressing

A page can be reachable at BOTH addresses at once. A named page toggled default
carries `as_regulary_by_name_username=[nik,name]` AND `as_default_by_username=
nik`, so it answers `/username/name` AND `/username`. One record, two link
addresses. The two username indices are NOT redundant; merging them breaks this.

## Corrected principle (the lens for the schema work)

"Any sacrifice for the first domain/username(/name) link." The page must be
directly addressable by `[username, name]` and by `[username]` in a single KV
lookup. We denormalize username onto the page and accept the rename cascade
(`update_nik` updateMany) because renames are rare and the link is hot. Sacrifice
writes/storage/complexity FOR the link, never the link for them.

## Genuine simplification room (without touching the sacred lookups)

- Drop vestigial `html`.
- Rename cryptic index fields to intention-revealing names, same behavior
  (`as_default_by_username` -> e.g. `default_at_username`,
  `as_regulary_by_name_username` -> `at_username_name`).
- Separate identity/routing fields from content fields in the DTO.
- Keep `user_id` (dashboard list, 135), `is_published` (profile filter, 187),
  `as_default_by_user_id` (`/id/:user_id` anon path).

## Open, concept-level (raise with user)

- How far to denormalize/precompute FOR the link: current 1-get-then-render vs
  cache rendered output by link (already done for pdf via Web Cache) vs store the
  rendered artifact under the link key for zero-render serving.
- No reserved-username guard: usernames share the root namespace with app routes
  (`/dashboard`, `/settings`, `/home`...). Works today only because no nik
  collides; a collision shadows an app route. The concept implies a reserved
  list is needed.
