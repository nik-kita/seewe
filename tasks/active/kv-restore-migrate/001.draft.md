# KV restore + forward migration (old CV schema -> new page schema)

## Goal

Consume a dump from [[kv-dump-script]] and load it into the new generic
share-page schema introduced by [[pivot-share-link-service]]. This is a
migration, not a verbatim restore: old CV-shaped records are transformed to the
new shape on the way in.

## Mapping (to finalize once the rename lands)

- `_dev_users` → carried as-is (auth/users are unchanged by the pivot).
- `_dev_md_cv` (CV record: `kind`, `md`, `css`, publish/default, name/username
  slugs) → new generic page collection + renamed fields. Exact target names
  depend on the noun chosen in the rename — BLOCKED on that decision.
- `_dev_md_cv_pdf` (chunked v8 blob) → new blob collection, bytes unchanged
  (binary payload is content-agnostic; just re-key to the new id).

## Requirements

- Re-runnable / idempotent.
- Restore into a fresh KV namespace (new prefixes) or separate DB, so old data
  is untouched until an explicit cutover.
- Post-load verification: per-collection counts match the dump, spot-check that
  a CV record + its pdf blob round-trip and still serve.

## Blocked on

- A dump existing (format from [[kv-dump-script]]).
- The new schema / field names from [[pivot-share-link-service]].

## Next (when unblocked)

Define the field map, write the restore script consuming the dump format, run it
against a fresh local KV, verify counts + a served page.
