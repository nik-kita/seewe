# Pivot: CV host → share-page-via-link service

## Why

The product is built around the CV as the central entity, but the underlying
mechanic is general: a user creates content, gets a public link, and controls
publish/default state. CV is one instance of that pattern. Reframing the core
unit as a generic shareable page (reachable by link) widens the product without
changing the serving mechanics.

## Current state (CV-shaped)

- Domain: `mdcv` records — `MdCvDto` with `kind: "md" | "pdf"`, `md`, `css`,
  publish/default flags, name/username slug fields (`as_default_by_user_id`,
  `as_default_by_username`, `as_regulary_by_name_username`).
- API: `/v1/mdcv` CRUD + `/pdf` sub-resource; blob bytes in a separate
  serialized KV collection (`_dev_md_cv_pdf`).
- Public serving: `/slug`, `/username`, `/slug.pdf`; md→html via the custom
  no-library renderer + user CSS; PDF served inline/download, read-through
  cached by `id/pdf_version/variant`.
- UI: dashboard ("Markdown CV" / "New CV from PDF" / `/pdf-cv` page), MD/PDF
  badges, published/default ToggleSwitches.

## Target framing

- Core noun becomes a generic shared page/link; CV is a content type, not the
  schema. Content types should extend beyond md/pdf without a new endpoint per
  type.
- Keep all serving, slug, publish/default, blob-storage, and caching machinery —
  it is already content-agnostic in mechanism, only CV-named in surface.

## Decision needed first (blocks planning)

Two paths with very different cost/risk:

1. **Thin rebrand** — UI + API wording only; `mdcv` collection, routes, and DTO
   field names stay. Fast, no migration, but the CV vocabulary lingers in code.
2. **Full rename + generalize** — rename collection/routes/DTO to a generic
   noun, model content types openly, with a compat/migration story for legacy
   CV records (which already default `kind:"md"`).

## Constraints carried in from memory

- Custom markdown renderer (src + api copies) — do not introduce a markdown
  library when generalizing content types. [[seewe-custom-markdown-renderer]]
- kvdex validates on write only; read defensively. Deno KV 64KiB value cap →
  binary payloads must stay in serialized collections.
  [[seewe-kvdex-write-only-validation-and-kv-limits]]

## Next

Resolve the rebrand-vs-rename decision, then decompose into a plan (schema,
routes, UI, migration). No code until the path is chosen.
